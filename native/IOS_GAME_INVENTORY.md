## Scope, shared dependencies and evidence

All campaign game roots are routed through `AppRouter`/lazy registry plus `GameLoadBoundary`. `App.tsx` supplies shared session, top HUD, orientation/Start gating and global utility dock. Scene/frame layers also come from `GameplayContentViewport`, `GameUiKit`, `GameplaySceneBackdrop`, `SceneEnvironment`, `vision-*` styles and game-specific CSS. Thus a local class alone is not necessarily the final geometry owner. Existing `native/GAME_START_REVIEW.md`, `PORTRAIT_GAMES_REVIEW.md`, `PRIME_POP_REVIEW.md`, `ZOMBIES_GROUNDING_REVIEW.md`, `BREATH_BLOOM_REVIEW.md` were consulted; do not redo their assertions as if they were fresh native results.

**Fresh evidence:** all 37 current campaign initial-play screens were visually inspected in `qa-artifacts/ios-aaa-audit/art-contact-1.jpg` through `art-contact-7.jpg`; individual images are `<key>-play.png` in the same directory and actual DOM bounds are in `results.json`. **F** denotes this fresh browser evidence, not native verification. The reduced contact sheets support composition review; exact text/hitbox conclusions use the individual captures and DOM measurements.

**Historical evidence labels:** V-local = visually reviewed existing `qa-artifacts/lightbulb-tips/<key>-play.png`; V-old = visually reviewed existing `qa-artifacts/game-dock-clearance/phone-<key>.png`; S = source inspected, screenshot verdict pending. These labels apply to this ledger's inspection, not a claim that other QA never captured the game. New audit capture findings should be linked separately by the main audit. Historical screenshots may show Help where the current local control is Tips.

No unconditional P0 is established by this source-ledger alone. P1 below means a significant candidate or demonstrated historical issue requiring current reproduction; P2 denotes composition/readability risk. Native iPhone/iPad testing is outstanding. Every game still needs results/failure/retry and loading/error coverage, not just a seeded initial question.

## Cross-game conclusions from this inventory

1. A single first-question capture per key is insufficient. Match/graph/shape/assessment and cargo games change layout by mode; tests must enumerate actual renderer states.
2. Touch size is separate from overlap. A clear dock does not make tiny board cells, graph ticks or drag handles usable.
3. Prefer typed layout capabilities (wide lane, square board, workstation, assessment, calm) over increasing per-key offset patches. Retain game-specific composition within shared safe bounds.
4. Source-only/dormant implementations should be tracked, not polished speculatively. Prove reachability first; do not expose new games as part of this audit.
5. Current Tips work is local and partial: a document-visible list does not prove the scroll viewport presents readable rules on short landscape. Include actual first-content visibility and keyboard/focus tests in the shared dialog batch.
